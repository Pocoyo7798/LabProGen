# Schema-derived Python models

`schema/action_data_model.yaml` is the source of truth for the semantic data
structure: classes, slots, types, inheritance, mixins, enums and constraints.
`labprogen/generated/action_data_model.py` contains the corresponding models
produced by LinkML's official Pydantic generator. Do not edit this file manually.
Its header identifies the schema hash and generator version; the schema's
[CC BY 4.0 attribution](../schema/README.md) also applies to the derived content.

## Regeneration

From the repository root, using the committed `uv.lock`:

```bash
uv run --locked python -m tools.generate_models
uv run --locked python -m tools.generate_models --check
uv run --locked --extra test python -m pytest
```

Commit schema changes and the regenerated module together. `--check` returns a
nonzero exit status if the generated file is missing or stale and writes nothing.
The check also verifies registered application and presentation references against the current schema. The test suite checks synchronization and generation in temporary schemas.
An intentional LinkML generator upgrade may change its output; regenerate and
review the module after updating the lockfile.

The generated code is versioned and included in wheel, sdist and PyInstaller
builds. Installation and application startup do not run code generation. This
keeps `pip`, `uv`, `uvx` and executable installation independent of a build-time
generation hook. Regeneration requires the full LinkML package, already used by
the project; the models themselves import Pydantic, not the Python generators.

The generation command adapts the schema in memory using the loader's existing
compatibility handling: the project-specific `closed` class flag is omitted
because the installed LinkML metamodel does not support it. No source schema is
rewritten. Generated models reject extra fields; the application retains its
strict unknown-field checks and official LinkML validation.

## Application boundaries

| Layer | Responsibility |
| --- | --- |
| `generated.action_data_model` | Typed semantic models, field declarations, enums, inheritance, mixins and generated metadata. |
| `linkml.models` | Look up generated classes and adapt semantic dictionaries with `to_model`. |
| `core.actions` / `core.chemicals` | Editable draft adapters with `.params`, attached chemicals, subproduct operations and serialization. Their `.model_class` and `.to_model()` refer to generated models. |
| `linkml.loader` / `core.model` | Official `SchemaView` induced slots, class-scoped field contracts, presentation merging and draft defaults from generated fields. Blank drafts are editing placeholders, not invented semantic values. |
| `core.protocol` | Application flows and canvas envelopes, import/export orchestration. These do not correspond directly to the schema's single `LabProcedure` record. |
| `complex` | User-defined grouping, bindings, registry and editing behavior, which are application concepts. |
| `ui` | Existing PySide6 widgets, canvas behavior and dialogs. No GUI code is generated. |

A new schema class gets a typed Python representation after regeneration.
Supporting its particular behavior or visual placement can still require normal
application changes. Legacy name aliases, unit display preferences and lossless
migration rules remain application code.

Example:

```python
from labprogen.generated.action_data_model import Cell
from labprogen.linkml.models import to_model

cell = Cell(passage_number=3)
cell.genetic_modifications = [{"construct": "pLab"}]
procedure = to_model({
    "laboratory_actions": [{"type": "NoAction", "duration": "1 min"}],
}, "LabProcedure")
data = procedure.model_dump(mode="json", exclude_none=True)
```

## Validation

The generator represents required/optional fields, scalar and list types,
subtype relations, type designators, enum values, supported defaults and
constraints such as minimum cardinality. Pydantic validates construction and
assignment, but may coerce values such as an integer string. Its class metadata
is not a complete implementation of every LinkML rule.

The export boundary therefore instantiates the generated models **and validates
the original dictionaries** using the existing strict checks and official LinkML
validator. It does not replace source data with coerced or defaulted output.
Required list presence, non-empty content, abstract classes and other semantic
policies must not be inferred solely from type hints or successful construction.
Incomplete and unsupported drafts remain available for explicit review.

## Structural metadata and presentation

Use `field_contract(slot, class_name)` or `field_config(slot, class_name)` from
`labprogen.core.model` for class-bound code. Contracts come from the official
[SchemaView](https://linkml.io/linkml/developers/schemaview.html) API:
`class_induced_slots` resolves inherited slots, mixins, `slot_usage` and inline
`attributes`. The returned metadata includes required flags, ranges, list and
inlining flags, defaults (`ifabsent`), numeric limits and cardinalities.
A field absent from that class has `declared=False`; another class's global slot
or attribute does not supply a fallback contract. Callers receive independent
copies and cannot change cached contracts.

`core.config.UI_FIELD_PREFERENCES` contains labels, placeholders, widget
preferences, suggested units and suggested input values. These suggestions are
not semantic defaults. Schema titles/descriptions provide label/placeholder
fallbacks; ranges, enum options, required flags and multiplicity always come
from LinkML. For example, `chemical` is a list on `Add` and a single object on
`MixtureConstituent`. There is no class-independent contract for both.
`FIELD_CONFIG` remains a compatibility projection of global slots for
context-free presentation; it must not be used to validate or edit a class.

`default_params` uses the generated model's fields and supported generated
defaults, with empty scalar/list/record placeholders where no value is defined.
New attributes and inherited fields do not need a new Python field table.
Chemical-valued fields and action families are discovered through schema ranges
and ancestry, including subclasses. Canvas attachments use the distinct semantic
role described below. Editor widgets consume this metadata directly.

## Application rules and compatibility

Keep these manual because they describe application behavior, not the model:

- Branch representation, action button labels/order, unit suggestions, custom
  labels and the Repeat positive-count editing rule. Canvas permissions are
  schema-derived as described below. Exempting a complex-action draft from
  attachment does not relax strict LinkML validation.
- Legacy class aliases and structural migrations in `core.config`, and legacy
  ontology slot conversions in `linkml.adapter`. Current slot names pass through
  unchanged rather than being duplicated in identity mapping tables.
- PubChem/text-generation behavior, canvas envelopes, complex-action bindings
  and other operations that have a specific semantic meaning in the application.

Historical editing hints are separated into `LEGACY_FIELD_PREFERENCES`. Their
presence cannot declare a current field or make it required. Undeclared fields
and incompatible historical shapes are shown as retained values for review;
editing another field preserves their original JSON values, including nested
objects and empty collections. They still fail strict export validation. A
migration or an explicit data correction is needed to make them valid; no
automatic rename is guessed and no data is silently discarded.

## Updating schema integrations

1. Edit/review the schema and regenerate the checked-in models with the commands
   above. Restart the application to reload its cached schema metadata.
2. Run `--check` and the tests. `KEY_*` names for current slots are checked schema
   references, not new declarations: missing names fail with an obsolete-reference
   error. `validate_schema_references()` also reports stale presentation fields,
   class-scoped label overrides, alias targets and registered GUI class anchors.
   Legitimate historical names are explicitly kept out of those current bindings.
3. Review any affected behavior before defining a migration. Update only the
   application bindings whose meaning changed; do not add a constant or widget
   preference for every new schema field.

A new class becomes available in generated models and the appropriate domain
family after regeneration. Its button, special canvas behavior or constrained
chemical picker can still need deliberate GUI integration. A renamed field
retains its chemical attachment role when the explicit annotation is preserved.
PubChem lookups and older protocol data require their own integration or migration.
Reference checks cover registered bindings, not arbitrary string literals or every
possible LinkML modeling feature. Changes to
such behavior and unsupported generator constraints need integration tests and
review; strict original-data validation remains the final boundary.

Evolution tests use temporary schema copies and official generation to cover new
properties/classes, defaults, required flags, enum additions/removals, removed
fields with historical data, different per-class contracts, inherited/mixin/inline
slots, cardinalities and preserved presentation preferences. The official schema
is never rewritten by these tests.

## Action capabilities

`core.capabilities.chemical_attachment_slot(class_name)` resolves the primary
chemical relationship from the effective LinkML fields of that class. A field
can declare this role independently of its name:

```yaml
chemical_entity:
  range: ChemicalEntity
  annotations:
    labprogen_chemical_attachment: true
```

`SchemaView.class_induced_slots` resolves the annotation through inheritance,
mixins, inline attributes and `slot_usage`. A marked field must have a range of
`ChemicalEntity` or one of its subclasses. Multiple true declarations, nonboolean
values and incompatible marked ranges are errors, also reported by
`validate_schema_references()` during the generation check. Any explicit role
declaration overrides the historical fallback; setting all declarations to false
disables it for that class. Other chemical-valued fields retain their ordinary
inline editors and never become attachment targets merely because of their range.

The current schema does not declare this annotation or an explicit `slot_uri`
for `chemical`. Unannotated classes therefore use the compatible effective field
named `chemical`. Renaming that field requires retaining an explicit role as in
the example; range alone does not identify the target. A global annotation also
propagates to `MixtureConstituent`, where the resolver identifies the composition
member relationship. It does not grant that chemical class a canvas permission.

`get_action_capabilities(name)` returns an immutable result containing
`allows_chemical_blocks`, `requires_chemical_relation` and the resolved
`chemical_slot`. Permission requires a concrete, non-mixin descendant of `Action`
with a resolved role. Unknown, abstract and non-action classes deny attachment.
Legacy class aliases are resolved by the import adapters.

`requires_canvas_chemical` checks the editing preflight separately. Optional
relationships allow attachments without requiring them; required relationships
may already contain inline values. Complex-action drafts retain their attachment
exemption, while strict export still requires a complete, valid relationship.
`core.config.action_requires_attached_chemical` delegates to this helper.

Dragging, target selection, previews, direct linking and domain `add_chemical`
use the same permission. Chemical stacks consult their owning action; standalone
stacks remain usable before attachment. Import reconstructs incompatible
historical links with warnings, retaining the records for review and strict
validation.

The editor, typed domain conversion, LinkML projection and reimport all use the
resolved destination name. Projection follows its class-specific multiplicity
and rejects conflicting inline and attached values. Canvas-owned fields retain
empty draft placeholders for complex-action bindings. Composition serialization
and its embedded entity picker use the resolved `MixtureConstituent` member
field as well. The native envelope key `chemical`, whose value is a class name,
remains an application format key independent of LinkML field names.

Role metadata identifies a current field, not a historical migration map.
Protocols containing a former field name retain it for review and fail strict
validation until explicitly migrated. Conflicting former/current fields are
preserved. Saved complex-action bindings and reusable definitions that name a
renamed field also require explicit migration.

After schema edits, regenerate models, restart the application and run `--check`
and the tests. Temporary-schema tests cover marked renames through canvas editing,
strict/optimized export, reimport, composition and complex-action snapshots.
Cardinalities and concrete entity types remain schema validation constraints.
Add's canvas-first editor and split export are separate presentation/export rules.
